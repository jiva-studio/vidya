# План: объединение Classroom и Vidya

Статус: черновик, согласован в обсуждении 18.09.2026. Один вопрос открыт — см. конец.

## Зачем этот документ

Vidya и Classroom — один продукт, разошедшийся на две кодовые базы. Classroom
писался раньше и имеет работающие админку и мобильное приложение, но без
мультиарендности. Vidya — переписанный бэкенд со школами и правами, но без
единой строчки фронтенда. Задача: собрать одно целое.

Конечная цель: админка, где заводят школу, назначают людей с правами, создают
курсы; мобильное приложение, которое выкачивает курс и работает офлайн —
студент проходит уроки и сдаёт домашки, преподаватель их проверяет.

### Критерий готовности v1

**Одна школа проводит один курс от начала до конца.** Школа заводит курс,
набирает студентов, те проходят уроки и сдают домашки, преподаватель проверяет.
Пока этот путь не пройден целиком, версия не готова — сколько бы этапов ни было
закрыто.

### Вне v1

- студенческий веб-кабинет — студент только через мобильное приложение
- чат и push-уведомления
- скачивание видео в офлайн: в v1 только эмбед (YouTube и подобные) при сети
- проверка домашек с мобильного — преподаватель работает в админке

Мультиарендность **входит** в v1, включая переключатель школ в интерфейсе.

## Принятые решения

### Синхронизация — из Lectorium, не managed

Рассматривались PowerSync и ElectricSQL. Отвергнуты: они реплицируют саму базу
Postgres на клиент, то есть встают вместо API. Задача другая — админка пишет
через REST, мобилка через REST выкачивает. Репликации БД здесь нет.

Готовой библиотеки под стек не существует. В Lectorium движок не пакет:

- порты и типы HLC — `libs/domain/ports/*`, `libs/domain/sync/types.ts`
- SQL-адаптеры, outbox, journal-декоратор — `apps/mobile/infra/repositories/sql/`
- сценарии `pullAndMerge` / `pushLocal` — `apps/mobile/usecases/sync/`

Клиентская часть ~2670 строк TypeScript — переносится копированием. Серверная
половина в Lectorium написана на Go (`services/profile`), поэтому у нас это два
эндпоинта на NestJS: `pull` с курсором и `push` с HLC.

Ключевое свойство, ради которого всё это берётся: каждое изменение пишется в
`outbox` **в той же транзакции**, что и доменная запись, со штампом Hybrid
Logical Clock. В Classroom синхронизация была наивной — `download*` перезаписывал
всё целиком, без курсора, без аплоада конфликтов, без атомарности.

### SQLite только на мобилке

Веб — и админка, и любой будущий кабинет — ходит в REST. Локальной базы там нет,
поэтому спор `sql.js` против OPFS не возникает вовсе. На устройстве
`@capacitor-community/sqlite` за портом `ports/app/persistence.ts`.

### UI — две библиотеки

- `libs/ui` — shadcn-vue + Tailwind 4, только веб
- мобилка — Ionic + `kit/ui`

Шарятся не компоненты, а слои под ними: `libs/domain`, `libs/protocol`,
`libs/usecases`.

Рассматривался PrimeVue: у него сильнее таблицы, но тяжёлых гридов в этом
проекте нет, а его unstyled-режим чинит внешний вид и не чинит поведение
компонента. Старые `CrudForm`/`CrudTable` из classroom-admin не переносим —
собираем заново на shadcn-vue.

### Один сервис, одна база

Микросервисов нет. `sync` и `media` — модули внутри `services/api`.
`services/database` растворяется: `.sql` переезжают в API, сущности остаются
в `libs/entities`.

### Контент — документ, результаты — строки

Уроки, секции и блоки хранятся **JSON-ом** в `lessons.content`. Причина: блоки
полиморфны (`video` / `audio` / `text` / `quiz` имеют разные поля), а
полиморфизм в SQL требует либо широкой таблицы с `NULL`, либо EAV, либо таблицы
на тип — и в любом случае JSON-колонки для `answers[]` и `timestamps[]`. Плюс
редактор: сохранение урока остаётся одним `UPDATE`, а не транзакционной
пересортировкой строк.

Условия, без которых это не работает:

- секции и блоки несут **устойчивые UUID**, выданные в редакторе при создании
- идентификаторы никогда не переиспользуются
- индекс массива идентификатором быть не может

### Версии уроков

Урок версионируется, у версии есть состояние «черновик» и «опубликовано».
Студенты видят только опубликованное. Преподаватель может вернуться к прошлой
версии и посмотреть, что менялось.

Домашка ссылается на **версию**, по которой отвечали, а не на текущий урок. Это
заменяет снимок: работа самодостаточна, потому что версия неизменяема после
публикации.

Если студент отвечал по версии 3, а опубликована уже 4 — работу **принимаем** и
помечаем расхождение. Проверяющий видит пометку и может открыть ту версию,
которую решал студент. Наказывать студента за правку, сделанную в его отсутствие,
нельзя.

Удаление секции со сданными работами запрещаем на уровне API.

Прогресс, ответы, домашки и оценки — обычные таблицы с обычными индексами.
Аналитика считается по ним, а не по контенту.

### Медиа — по источнику

Блок несёт дискриминатор:

    { "type": "video", "source": "upload",  "url": "…" }   → можно скачать
    { "type": "video", "source": "youtube", "id":  "…" }   → только встроить

Клиент смотрит на `source`. В v1 поддержан только эмбед — видео смотрится при
сети. Дискриминатор закладываем в модель сразу, чтобы скачивание добавлялось
без миграции схемы и без правки уже созданного контента.

### Локализация

Fluent (`.ftl`), локали en и ru уже написаны в classroom. Оставляем.

## Модель доступа

Две независимые оси, смешивать нельзя:

- **Сотрудник школы** — `PermissionKey` со скоупом по `schoolId`. Уже работает.
- **Студент** — аккаунт плюс записи на курсы. Прав в этом смысле нет, доступ
  даёт `enrollment`. Записей у одного студента несколько.

Каталог курсов виден студенту без записи.

В v1 мобильное приложение — приложение студента. Преподаватель проверяет работы
в админке, где удобнее читать развёрнутые ответы. Мобильная проверка — следующий
релиз; правила видимости в синхронизации проектируем с расчётом на неё, но второй
набор экранов не пишем.

### Запись на курс

С модерацией. Запись идёт **на курс**, `groupId` остаётся пустым; группа
назначается потом отдельным действием. Студент может записаться, когда групп
ещё нет, и ждать в очереди, пока подходящая не появится.

В схеме это уже заложено: `enrollment.groupId` nullable, `groups.courseId NOT NULL`.

### Домашки

Цикл: `open → pending → in-review → returned → accepted`. На `accepted`
выставляется оценка. Проверяет преподаватель, с возможностью вернуть на
доработку. Автопроверка квизов — этап 2, не в первой версии.

Два правила снимают весь класс конфликтов:

- **Статус решает только сервер.** Клиент умеет отправить работу, но не умеет
  перевести её в `accepted` или `returned`.
- **Отправка замораживает ответ.** После `submit` текст не редактируется до
  возврата на доработку.

Остаётся единственный граничный случай: работа ушла в offline-очереди, а на
сервере её уже приняли. Тогда push отклоняется с понятным сообщением — «работа
уже принята», — и локальная копия помечается как устаревшая. Клиент и сервер
никогда не пишут одно и то же поле, поэтому сливать нечего.

Бэкенда под домашки не существует нигде: в Classroom они жили только как агрегат
на мобилке. Проектируются с нуля.

## Офлайн-авторизация

Токен управляет сетью, а не локальными данными. Три вещи, которые нельзя слипать:

1. **Чтение скачанного — безусловно.** Контент уже лежит в SQLite на устройстве.
   Закрывать его по истечении токена бессмысленно: данные физически там.
2. **Запись в outbox — безусловно.** Домашка пишется при любом состоянии сессии.
   Потерять работу студента из-за протухшего токена — худший возможный отказ.
3. **Приём решает сервер.** На `push` проверяются личность и права. Отчислили
   студента — push отклоняется **с причиной**, работа остаётся на устройстве,
   интерфейс объясняет.

Следствия для реализации:

- Время жизни токенов переворачиваем. Сейчас в `jwt.config.ts` access живёт
  15 дней, а refresh — 7: обновить сессию нельзя уже через неделю, при живом
  ещё access. Должно быть наоборот — короткий access, длинный refresh, месяцы
  для студенческих мобильных сессий.
- Строки outbox несут личность, под которой созданы. В Lectorium это учтено:
  watermark `pushed_outbox_id` снимает строки либо после отправки, либо при
  смене владельца.
- Отказ в приёме — состояние строки, а не всплывашка. Статус на каждую строку,
  чтобы одна отклонённая не блокировала остальные.
- Строки outbox не удаляются молча. Никогда.

## Синхронизация: что и куда

| Данные | Направление |
|---|---|
| курсы, уроки, секции, блоки | только вниз |
| прогресс по блокам | вверх |
| ответы на домашки | вверх |
| статус проверки и оценка | вниз |
| запись на курс | вверх (подача), вниз (решение) |
| сданные работы для преподавателя | вниз |
| оценки от преподавателя | вверх |

Студент может учиться в нескольких школах, поэтому синхронизируемые строки несут
`schoolId`, а локальная база остаётся **одна**: курсоры синхронизации привязаны
к личности, а не к школе. Раскладку закладываем так сразу — иначе потом миграция
на устройствах пользователей.

## Целевая структура

    modules/
    ├── libs/
    │   ├── domain/        сущности, инварианты, порты. Ноль зависимостей
    │   ├── protocol/      контракты по проводу, включая модель уроков
    │   ├── persistence/   типы строк клиентской БД
    │   ├── usecases/      сценарии, общие для веба и мобилки
    │   └── ui/            shadcn-vue + Tailwind 4 — только веб
    ├── apps/
    │   ├── admin/         Vue 3 + Vite
    │   └── mobile/        Ionic 8 + Capacitor 8 + kit
    ├── plugins/           нативные Capacitor-плагины
    └── services/
        └── api/           NestJS: edu, auth, sync, media — модулями

Мобильное приложение раскладывается гексагонально, как в Lectorium:
`ports/` (интерфейсы) → `infra/` (адаптеры) → `usecases/` (сценарии) → `ui/`.
Адаптеры не импортируют друг друга — только порты и домен.

## Миграции

Две независимые системы. Общего между ними нет ничего, кроме имён сущностей.

| | Сервер | Устройство |
|---|---|---|
| Что | `.sql`-файлы, руками | TS-миграции, руками |
| Кто катит | API при старте, до `listen()` | приложение при старте |
| Учёт | `schema_migrations` | `migrations` (`kit/persistence`) |
| Направление | только вперёд | только вперёд |

Генераторы схемы из ORM (Atlas, `typeorm migration:generate`) отвергнуты: в
миграциях сюрпризы дороже всего, SQL пишем сами.

Восемь существующих миграций переносятся в `.sql` механически — SQL уже написан
руками внутри `queryRunner.query()`.

### Требования к раннеру

1. Отдельное соединение, **не из пула**: advisory lock у Postgres сессионный.
2. Каждый файл в своей транзакции.
3. Пустая папка миграций — ошибка, а не успех. Иначе `.sql` не попадут в образ,
   раннер отчитается об успехе, и приложение упадёт на первом запросе.
4. Файлы копируются в Docker-образ явно, путь берётся из `VIDYA_MIGRATIONS_DIR`.

Откат делается новой миграцией: откатив образ, схему не откатишь. `down` не пишем.

Сиды (`@vidya/seeder`) при старте **не** запускаются — только `make seed`.

### Попутно

`services/database/main.ts` захардкожен на `localhost` / `postgres` / `postgres`.
Исчезает вместе с переносом миграций в API, где конфиг уже берётся из окружения
(`VIDYA_DB_*`).

`synchronize` у TypeORM нигде не включён — проверено.

## Этапы

**1. Фундамент.** Модель уроков (секции → блоки) в `libs/protocol`. Ключи прав
`courses` / `lessons` / `groups`. Сущности и таблицы `enrollments`, `homework`,
`progress`. Перенос восьми миграций в `.sql` плюс раннер в API.
Версии: NestJS 11, Node 22, Vue 3.5, Tailwind 4, Ionic 8, Capacitor 8.

**2. API обучения.** `edu/courses`, `edu/lessons`, `edu/groups`,
`edu/enrollments`, `edu/homework` — по образцу classroom-backend, но со скоупами
и тестами в стиле существующих 78. Снимает блокировку со всего остального.

**3. Синхронизация.** Перенос outbox, HLC и курсоров из Lectorium. На сервере —
`pull` и `push` с серверной валидацией. Порт `ports/app/persistence.ts` и адаптер
под Capacitor.

**4. `libs/ui`.** shadcn-vue + Tailwind 4 с нуля. Из classroom-admin берём только
раскладку экранов и локали.

**4a. Редактор уроков.** Простой визуальный блочный редактор в админке: добавить
текст, видео, аудио, квиз; поменять порядок; предпросмотр; черновик и публикация
версии. Markdown не используем — контент и так блочный, промежуточный формат
только добавил бы преобразование в обе стороны. Это отдельная работа
сопоставимого размера с остальной админкой, и без неё школе нечего отдать.

**5. Админка.** OTP, школы, роли, пользователи, курсы, группы, модерация записей,
проверка домашек.

**6. Мобилка.** Перенос агрегатов и сценариев, PouchDB выбрасывается, SQLite за
портом `ports/app/persistence.ts`. Офлайн-чтение курса и запись домашек в outbox.

Основная часть этого приехала вместе с этапом 3: гексагональная раскладка,
адаптер SQLite под Capacitor и миграции устройства, репозитории, сценарии
обучения, экраны курсов, урока, записи и домашки, офлайн-слой в интерфейсе.
`kit` не подключён — см. ниже. Остаток разбирается на шесть кусков.

**6a. Подключения.** Приложение ходит не на один сервер. Единица —
*подключение*: `{ сервер, сессия, состояние синхронизации }`. Пользователю оно
не показывается никогда: он видит только школы.

`connection_id` входит в ключи `sync_state` и `sync_scopes`, сессия хранится на
подключение, движок синхронизации создаётся на подключение, обновление токена
идёт молча по всем — включая те, на чью школу сейчас не смотрят.

Делается первым и до релиза. Миграций устройства сейчас две, баз у пользователей
нет; после релиза это миграция на чужих телефонах.

**6b. Каталог едет синхронизацией.** Сегодня `CoursesListPage` берёт каталог по
сети, и другого источника у него нет: `SyncScopesService.scopesFor()` выдаёт
`user:<id>` и `course:<id>` по принятым записям, а грант `school:<id>` не
выдаётся никому. Курса, на который студент не записан, на устройстве нет.

Вид скоупа `school` уже объявлен, журнал уже штампует `school_id` — не хватает
двух вещей:

- грант `school:<id>` по `getUserSchools(userId)`;
- **курс проецируется дважды**: витрина (имя, описание, тип обучения) — в
  `school:<id>`, содержимое (уроки, версии, секции) — в `course:<id>`. Без этого
  грант школы утащит на устройство контент курсов, куда студента не приняли.

После этого экран читает каталог из `ports/data` и работает офлайн.

**6c. Подключение школы по ключу.** Школа и сервер зашиваются при сборке —
white label. Всё остальное добавляется ключом.

Ключ — постоянный публичный код школы, 6 символов base32, живущий в ссылке вида
`school.ru/j/AB3K7Q`. Домен внутри ключа, поэтому центральный реестр серверов не
нужен. Основной путь — QR или deep link, пользователь не вводит ничего; ручной
ввод той же строки — запасной. UUID школы не вводится никогда.

Публичный резолв `GET /j/<код>` без токена отдаёт `{ schoolId, name, logoUrl }`
— карточка «Добавить школу?» показывается до всякой авторизации.
Дальше приложение сравнивает домен с уже подключёнными:

| Что произошло | Что делает приложение |
|---|---|
| Первый запуск | Авторизация на зашитом сервере, зашитая школа активна |
| Школа того же сервера | Токен уже есть — школа появляется на главной |
| Школа чужого сервера | Тот же экран OTP, но поверх нового подключения |

Экраны авторизации переиспользуются как есть.

Принадлежность к школе **не заводит новой сущности**: она уже выражена ролью.
`UserSchoolsService.addUser` выдаёт `school.config.defaultStudentRoleId`,
`getUserSchools` отдаёт школы по ролям, маршруты `/edu/users/:id/schools`
написаны. Подключение школы — это `POST` на них.

**6d. Одна лента.** Переключателя школ нет. Курсы всех подключённых школ лежат
на главной вместе, карточка несёт метку школы. Синхронизация идёт по всем
подключениям сразу: домашка не должна ждать, пока на её школу переключатся.

Школе добавляются `logoUrl` и `description`. Языка у школы **нет** и логики,
завязанной на язык, не появляется: школа спокойно ведёт курсы на разных языках,
поэтому язык — не её свойство. Язык приложения остаётся системным.

`logoUrl` — внешняя ссылка. Байты в базу не тянем: это был бы зачаток медиа-слоя,
а он этап 7. Логотип не загрузился — рисуем первую букву названия.

**6e. Нативная сборка.** `capacitor.config.ts` до сих пор объявляет
`com.akdasa.classroom` / «Classroom» — наследство архива, как и папки `android/`
и `ios/`. Ребрендинг, плагин камеры под QR, universal links на обеих
платформах, профиль окружения вместо `localhost:8080` по умолчанию.

Главное здесь не переименование: `@capacitor-community/sqlite` проверен только
конформанс-тестами через sql.js и **на устройстве не запускался ни разу**.

**6f. Настройки.** `ui/settings/routes.ts` пуст. Нужен минимум: список
подключённых школ, добавить и убрать школу, выход из аккаунта, состояние
синхронизации.

Порядок: 6a → 6b → **6e** → 6c → 6d, 6f параллельно.

6e поднят вперёд намеренно. Сканер QR живёт на камере, а нативная сборка ещё ни
разу не собиралась: `@capacitor-community/sqlite` проверен только конформанс-
тестами через sql.js. Писать 6c до первого запуска на устройстве — значит
проверять его обещанием.

**7. Медиа.** В Classroom `media`-контроллер был заглушкой: `console.log`, файл
никуда не сохранялся. Нужны хранилище и подписанные ссылки.

Порядок: 1 → 2 строго последовательно. Дальше 3 и 4 параллельно, затем 4a, 5 и 6.
Этапы 1–5 закрыты и влиты в main. В работе — 6.

Критерий v1 закрывается только когда сойдутся 5 и 6: админка заводит курс,
мобилка его проходит. Этап 7 в v1 не входит — видео только эмбедом.

## Что прожарка изменила в этом плане

Список ведётся, чтобы решения не пересматривались по кругу.

- Появился критерий готовности v1 и явные границы «вне v1».
- Полный офлайн со всем движком синхронизации подтверждён как core-функция
  первой версии, а не как то, что можно урезать.
- Найден **этап 4a**: блочный редактор нигде не был заложен, хотя без него
  контент неоткуда взять.
- Снимок секции в домашке заменён на **версионирование уроков** — работа
  ссылается на неизменяемую опубликованную версию.
- Зафиксированы два правила, снимающие конфликты домашек: статус только с
  сервера, отправка замораживает ответ.
- Описана офлайн-авторизация и найден перевёрнутый срок жизни токенов.
- Мобильная проверка работ убрана из v1 — преподаватель работает в админке.
- Скачивание видео убрано из v1, остался только эмбед.
- Мультиарендность подтверждена в v1, включая переключатель школ.
- `kit` не подключается. План обещал «SQLite через `kit`» и «мобилка — Ionic +
  `kit/ui`»; по факту написаны свой адаптер persistence и свой `design/`. Они
  работают и покрыты тестами — переписывать рабочее под библиотеку смысла нет.
- Этап 6 переписан под остаток: синхронизация привезла бо́льшую часть мобилки,
  зато вскрылись подключения к нескольким серверам, каталог без гранта школы и
  непроверенная нативная сборка.
- Переключатель школ на мобилке отменён: одна общая лента курсов из всех
  подключённых школ. Переключение остаётся в админке, где сотрудник работает
  в одной школе за раз.
